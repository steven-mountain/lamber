## 2. B 的覆盖契约缺少桌面联动语义

B4仅描述保存快照+`subject / inclTax / taxRate`覆盖，但桌面编辑不是单纯替换这两个字段：

- `src-ui/src/hooks/useIctState.ts:691`：金额或税率编辑会清除该科目的 `splitParts`，重新处理不含税金额；税率改动还受当前财务自动修正设置影响。
- `src-ui/src/hooks/useIctState.ts:721`：编辑CT产品收入会联动其他产品成本；专线收入会联动专线带宽成本。任务书“只接受具名覆盖”未说明是否允许这些隐含科目变更，也未规定显式覆盖与联动冲突的优先级。
- `src-ui/src/hooks/useIctState.ts:756`：金额变更同步资金计划。
- `src-ui/src/lib/ictSubjectFundingPlan.ts:760`：资金计划可能按比例重算、按原年度金额比例缩放、金额归零删计划、缺计划时创建默认首年计划。
- `src-ui/src/lib/ictCalculationInput.ts:45`：由科目资金计划重建四组税前年现金流：`rev_cashflow_excl`、`cost_cashflow_excl`、`it_rev_cashflow_excl`、`it_cost_cashflow_excl`。
- `src-tauri/src/benefit/calculator.rs:178`、`:187`、`:198`：引擎优先使用保存的四组年度数组，而非重新从科目合计计算；因此只改 `IctItem`、保留数组会使现金流和NPV仍引用旧金额。这是源码确认的失败路径，本轮未用新增工具冒充运行证据。

所以“覆盖后指标与桌面一致”无法由“克隆快照、改科目、调用Rust”直接保证。也不能清空年度数组让引擎降级到分布比例，那会改变已有收付款时序。

建议补齐后再施工：

1. 无覆盖时原样重放快照，保证与已保存计算逐字段一致。
2. 有覆盖时复用/抽取桌面的纯输入转换与资金计划同步规则，在内存副本完成；不重写第二套金额、分配与税额规则，不接入D搜索/承接逻辑。
3. 明确CT联动是否允许：若以桌面编辑为标准，返回应区分“用户显式覆盖”和“规则联动”，把所有受影响科目与计划列入前后对照；重复或冲突覆盖应明确拒绝，不能依赖数组顺序悄悄决定。若坚持仅改变具名科目，则须规定关联科目如何显式授权及桌面对照方法，不能假装两种语义相同。
4. 明确税额自动修正设置来源，以及无法从旧快照还原资金计划时的拒绝规则，不能自行假设首年或比例。
5. A的读取证据除逐科目金额/税率/名称/拆分外，应标明实际现金流来源；B除指标方向外对照全部结果字段和逐年现金流，并证明快照版本与正式数据不变。

这些是建议，尚未作为已批准契约实施。
