```
reason      用户已确认
requested_at 2026-09-03T03:52:28.498641+00:00
decided_at   2026-09-03T03:52:32.491109+00:00
```

工具确实在批准后才执行，标记文件内容：

```
写入时间: 2026-09-03T03:52:32.505Z
备注: 真实点击联调
```

决定落库时间 `03:52:32.491` → 文件写入 `03:52:32.505`，相差 14 毫秒，顺序正确（先批准、后执行）。审计记录写入的是**真实工作区数据库**，不是测试库。

## 3. 点「拒绝」 ✅

真实鼠标点击（由仓库所有者本人操作）：

```
approved     0
decided_by   user
reason       用户已拒绝
decided_at   2026-09-03T04:01:49.412659+00:00
```

拒绝后**没有产生新的标记文件**（临时目录里最新的仍是 `marker-2026-09-03T03-52-32-505Z.txt`，即第 2 项确认时那一次）。工具确实没有执行。

注意 `decided_by` 为 `user` 而非 `timeout`，可与第 4 项区分：这是人点的拒绝，不是超时兜底。

## 4. 不操作，等待 90 秒超时 ✅

同样以持久化审计表为证据。启动后不触碰弹窗，90 秒后：

```
approved     0
decided_by   timeout
reason       等待用户确认超时（90 秒），按拒绝处理
decided_at   2026-09-03T03:59:18.423375+00:00
```

并且**没有产生新的标记文件**——临时目录里最新的标记仍是第 2 项确认时留下的 `marker-2026-09-03T03-52-32-505Z.txt`。即超时判拒之后工具确实没有执行，不是"先执行再记一笔拒绝"。

倒计时文案与后端 `timeout_seconds` 一致（弹窗显示"89 秒后自动拒绝"，后端默认 90 秒，差 1 秒是渲染时已过去的一秒）。

## 已知问题与偏差

（本节记录与预期不符之处；若为空表示逐项符合预期。）

- **功能层面：无。** 四项均与预期一致，未发现弹窗未渲染、按钮点不动、被遮罩挡住或状态不同步的情况。
- **过程中的一次自身失误（非产品问题）：** 第一次尝试启动"拒绝"这一轮时用了相对路径且当时 shell 工作目录已被切换，应用其实没启动（`nohup: ... No such file or directory`）。当时一度怀疑是退出钩子没记 `shutdown` 记录，排查后确认是启动失败、根本没有待决审批。改用绝对路径后正常。记录在此以免日后看审计日志时对这段空档产生误解。

## 关于截图的取证方式

全屏截图会连带拍到桌面上其他窗口的私有内容，因此**不采用全屏截图作为常规证据**：仅保留一张启动瞬间（应用必然在最前）的窗口截图用于证明渲染，其余结论一律以持久化审计表 `agent_approval_log` 与文件系统产物为准——这两者比截图更难伪造，也更贴近"事后可追溯"的验收目标。
