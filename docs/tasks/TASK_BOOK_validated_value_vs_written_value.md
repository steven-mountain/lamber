# 任务书：校验的值不是写入的值——财务口径归一发生在校验之后

> **触发**：2026-09-10 D 轮推进时发现。锁定总额 100.00，
> 校验通过的候选是 **41.33 + 58.67 = 100.00**，
> 自动修正后实际写入 **41.34 + 58.67 = 100.01**。
> `updateTaxItemsInclBatch` 实测调用 **1 次**，**仍返回成功**，年度计划也跟着变了。
>
> 🔴 **D 件在本书完成前不得标记验收通过。**
> **卡片事后警告解决不了这个问题——钱已经写进去了。**

## 根因：写入端会二次改数，而校验发生在改数之前

`useIctState.ts:570-581` 的 `itemFromIncl`：

```js
const pair = normalizeTaxPairFromIncl(isNaN(incl) ? 0 : incl, tax);
return {
  ...
  incl: isTaxInclAutoFixEnabled() ? pair.incl : pair.enteredIncl,   // ← 开启自动修正时写的是 pair.incl
  excl: pair.excl,
};
```

`normalizeTaxPairFromIncl` 做的是"含税 → 不含税 → 再反推含税"的往返，
**结果可能与传入值差 1 分**。批量写入时**逐项独立归一**，
所以两项各自 ±0.01，合计就可能偏离锁定总额。

而结构反算的 `totalCheck`（`useIctCalculations.ts:990` 一带）
校验的是 `finalPoint.targetAmount + finalPoint.balancingAmount`——
**归一之前的值**。

> 该函数的注释本身就写着"**由界面提示与生成前校验兜底**"，
> 说明它假定**后面还有一道检查**。
> 但结构反算的检查在**前面**，兜底根本没接上。

## 🔴 更严重的连带：上一轮刚加的达标校验也是在非最终值上做的

`evaluate(targetAmount)` → `buildLockedTotalStructureCandidate(...)` → `candidate.payload`
→ `invoke("calculate_ict_benefit", { input: candidate.payload })`

**`candidate.payload` 用的是未归一的金额**，所以：

- `finalPoint.metricValue` 是**未归一状态**下的指标
- `:997` 新加的 `Math.abs(finalPoint.metricValue - target) > METRIC_EPSILON` 判定
  **判的也是未归一状态**
- 归一后写进去的那份状态，指标**可能已经落在 `METRIC_EPSILON` 之外**

→ **上一轮"未达标不写入"的修复，在开启自动修正时并不成立。**
本书不修这一处，那一轮的成果就是半截的。

## 🔴 同一形状的第四次

| # | 位置 | 形状 |
| --- | --- | --- |
| 1 | 甄选费反算（已修） | 区间检查假设函数连续 → 返回不存在的报价 |
| 2 | 收款计划清零（已修） | 恢复机制存在，被上游 `delete` 架空 |
| 3 | 结构反算达标（已修） | 只校验"自洽"，不校验"达标" |
| 4 | **本书** | **校验的值 ≠ 写入的值**，归一发生在校验之后 |

第 3、4 条是同一句话的两面：**守卫没守住它以为在守的东西。**

**建议写进 `AGENTS.md` 的第二条通则**（第一条见结构反算那本）：

> **校验必须作用在"将要写入的那个值"上，不能作用在它的前身。**
> 本项目的写入端（`itemFromIncl`）会按财务口径二次归一，
> **任何在调用 `updateTaxItemsInclBatch` 之前算出的结论，都不保证在写入后仍成立。**

## 要做的事

1. **把归一提前到候选构造阶段**：`evaluate()` 构造候选时，
   就用与 `itemFromIncl` **完全相同的归一逻辑**处理目标科目与承接科目金额，
   使**搜索、校验、写入三者面对同一组数字**。
   > **复用 `normalizeTaxPairFromIncl`，不要另写一份**——
   > 两份归一逻辑不一致，就是本项目栽过多次的形状。

2. **归一后重算同侧总额**：若归一导致合计偏离锁定总额，
   **由承接科目吸收该差额后再归一一次**；
   若仍无法闭合（例如差额小于 1 分无法分配），**报错并停止写入**，
   不要写一个 100.01。

3. **达标校验必须基于归一后的候选**（本书第二节）。

4. **`isTaxInclAutoFixEnabled()` 关闭时同样要正确**：
   此时写入的是 `pair.enteredIncl`（原值），校验与写入天然一致，
   但**两条分支都要有测试**，不要只测开启态。

5. **检查同一模式的其他调用点**：
   `useIctCalculations.ts:432`（甄选限价回填）在写入前有
   `normalizeTaxPairFromIncl` 检查，但**只在自动修正关闭时执行**
   （`if (!isTaxInclAutoFixEnabled())`）——
   **开启自动修正时它同样没有校验最终值**。一并确认是否需要同样处理。

## 不要做的事

- **不要靠"事后警告"或"卡片提示"来兜这个问题**——钱已经写了。
- **不要放宽 `MONEY_EPSILON` 让 100.01 通过**。锁定总额就是锁定总额。
- **不要关闭或绕过财务口径自动修正**来回避归一。那是既有的正确行为。
- **不要另写一份归一逻辑**，复用 `normalizeTaxPairFromIncl`。
- **不要自动改写用户的目标值**（沿用上一本的约束）。
- 不改二分搜索策略、`METRIC_EPSILON`、`MONEY_EPSILON`、财务公式。

## 验证要求

1. **原始复现**：锁定总额 100.00、候选 41.33 + 58.67、开启自动修正，
   确认**要么写入后合计仍是 100.00，要么明确报错并零写入**，
   不再出现 100.01 且报成功。
2. **零写入断言**：所有失败路径下 `updateTaxItemsInclBatch` **调用次数为 0**
   （沿用上一轮 35 个场景的做法）。
3. 🔴 **达标校验基于最终值**：构造"归一前达标、归一后超出 `METRIC_EPSILON`"的场景，
   确认**报错而不是写入**。
4. **两条分支都测**：自动修正**开启**与**关闭**各跑一遍全部场景。
5. **年度计划一致性**：写入被拒时，**科目收付款计划也未被改动**
   （本次现象里"年度计划也变化"是连带损伤）。
6. **甄选限价回填**（`:432`）在自动修正开启时的行为已确认或已同样修复。
7. **正常路径不回归**：候选本就在财务口径不动点上时，行为与修复前一致。
8. 前端 lint/build、既有反算与资金计划测试、相关回归通过；
   结果记入 `docs/verification/`。

## 附：为什么这轮必须停

D 的卡片设计里，用户点击即确认，**点击之后没有第二次把关**。
若底层能在"校验通过"之后把 100.00 写成 100.01，
卡片展示的"变更前 → 变更后"就是**一份和数据库不一致的对照表**——
用户核对的是卡片，实际生效的是另一组数字。

**这正是本任务书主线"错的和对的长得一样"的最后一种形态：
连给用户看的那份对照，都不是真的。**
