# 任务书：跨项目查询与汇总（只读）

> **位置**：路线图 [ROADMAP_ai_capabilities.md](./ROADMAP_ai_capabilities.md) 第 ③ 项。
> 前置 ①② 已完成。本文是第一个**新增**的业务工具，也是"聚合只读豁免"这条口子的唯一开口。

## 目标

让用户能问"去年毛利率低于 20% 的项目有哪些""这个客户做过几个项目""在手项目总投入多少"，
AI 通过参数化检索工具回答，而不是靠上下文里塞进去的当前项目。

## 先把风险模型摆正（决定了白名单怎么划）

②的硬性限权防的是**模型跑去操作别的项目**。到了只读汇总这里，威胁模型换了，
容易被想当然地当成"防泄露"，其实不是：

- **不是防泄露。** 整个工作区都是同一个用户自己的数据，模型现在已经能看到当前项目的
  完整成本与报价（上下文注入）。给它看其他项目的**汇总值**，不构成新的泄露面。
- **真正的风险有两条**：
  1. **模型混淆**——拿别的项目的数字回答当前项目的问题。这条**高发且危害实在**：
     用户问"我这个项目毛利率多少"，模型答成了检索结果里另一个项目的。
  2. **上下文膨胀**——几百个项目的汇总塞进 prompt，挤掉真正相关的上下文。

**所以白名单的目的是控体积和防混淆，不是防泄露。** 这个定位错了，会写出一套
既挡不住混淆、又把有用字段挡光的规则。

## 已确认的关键事实（写代码前不用重新调研）

### 1. 汇总数据就在 `projects` 表一行里，不需要 JOIN 明细表

`projects` 表（`db.rs:12-34`）本身就带项目级汇总：

- 身份：`id`、`name`、`customer_name`、`status`、`benefit_status`
- 时间：`created_at`、`updated_at`、`deadline`、`progress`
- 测算参数：`project_years`、`discount_rate`、`cashflow_model`
- **项目级金额**：`total_revenue_incl`、`total_cost_incl`
- **指标 JSON**：`summary_metrics` → `SummaryMetrics { margin_rate, npv, npv_rate, irr,
  dynamic_payback, risk_level }`（`benefit/models.rs:211-218`）
- 本机路径：`folder_path`、`main_document_path`、`main_budget_file_path`
- 自由文本：`note`、`logs`

### 2. 因此可以定一条结构性规则，而不是逐字段维护白名单

**实现规则：只读 `projects` 表的行 + 解析 `summary_metrics`，不 JOIN 任何明细表。**

这条比列字段清单更可靠——科目级明细、报价、供应商、甄选数据都在
`benefit_schemes` / `benefit_snapshots` / 模板状态等表里，只要不 JOIN 就天然进不来，
不会因为将来加了字段而漏网。

### 3. 已有可复用的读取入口

`get_projects`（`benefit/commands.rs:17`）已经在读这张表。
按惯例（路线图"架构决定"）**包一层，不要新写 SQL**。

### 4. ②的绑定校验不认识"没有 projectId 的工具"

②的校验逻辑是"请求的 projectId 与绑定的 projectId 比对"。
而汇总工具**没有 projectId 参数**，它天然跨项目——现有校验会直接把它判成异常。
所以必须显式新增一类"聚合只读"处理，且**必须是工具名白名单，fail closed**，
不能写成"没有 projectId 就放行"（那等于给所有未来的工具开了后门）。

## 要做的事

1. **新增只读工具 `query_projects`**（名字可调），参数化检索：
   - 过滤：客户名（模糊）、状态、`benefit_status`、时间范围（created/updated）、
     金额区间（`total_revenue_incl` / `total_cost_incl`）、指标区间（毛利率、NPV率等）
   - 排序 + `limit`，**`limit` 必须有服务端硬上限**（防上下文膨胀，见风险模型第 2 条）
   - 超过上限时返回"命中 N 条，仅返回前 M 条"，而不是静默截断
2. **可返回字段**（按关键事实 2 的结构性规则，落到具体就是）：
   - `id`、`name`、`customer_name`、`status`、`benefit_status`
   - `created_at`、`updated_at`、`progress`
   - `project_years`、`discount_rate`
   - `total_revenue_incl`、`total_cost_incl`
   - `summary_metrics` 的六个指标
3. **明确禁止返回**：
   - 任何本机路径（`folder_path`、`main_document_path`、`main_budget_file_path`）——
     对模型无用，且会把本机目录结构送进上游
   - `note`、`logs`——自由文本，内容不可控
   - 任何需要 JOIN 明细表才能拿到的东西（科目、报价、供应商、甄选、模板表单）
4. **结果必须自带"这不是当前项目"的标注。** 这是防混淆的主要手段，比字段裁剪更管用：
   每条结果显式带项目名，且工具结果里加一句固定说明，
   大意是"以下为跨项目检索结果，不得用作当前绑定项目的测算结论"。
   同时**当前绑定项目在结果中要标出来**（如果它命中了），让模型能区分。
5. **在②的校验里新增"聚合只读"分类**（关键事实 4）：按工具名白名单放行，
   其余一切照旧走 projectId 比对。白名单为空、或工具落不进任何已知分类时，一律拒绝。
   **通用聊天会话对该类工具放行、对其余工具仍全部拒绝**（见"已定口径"的二维表）。
6. 不需要审批（先例：`run_benefit_calculation` 不在 `GATED_TOOLS` 里）。

## 已定口径：通用聊天可用聚合工具（2026-09-06 用户确认）

**通用聊天会话允许调用聚合只读工具，且只允许这一类。**

- ②的原口径是"通用聊天禁用全部工具"，**本条修订它**——已在
  `TASK_BOOK_cowork_session_project_binding.md` 的"本轮执行口径"处标注。
- 理由：跨项目汇总不属于任何单个项目。若维持全面禁用，用户为了问一句
  "今年整体情况怎么样"就得先随便绑一个项目，体验上说不通，而且会**诱导用户乱绑**——
  乱绑出来的会话后续再做别的事时，绑定就成了误导而非保护。
- **边界**：通用聊天里除聚合只读工具外，其余工具**仍然全部禁用**。
  尤其是所有写工具（路线图 ④⑥），不因本条而松动。

因此校验分类有两个维度，都要 fail closed：

| 会话类型 | 聚合只读工具 | 其他工具 |
| --- | --- | --- |
| 绑定了项目 | 放行 | 按 projectId 比对，跨项目拒绝 |
| 通用聊天 | 放行 | **全部拒绝** |

工具名白名单为空、或工具不在任何已知分类里时，一律**拒绝**。

## 不要做的事

- **不开放 SQL、不开放自由查询表达式。** 只有参数化过滤（路线图"架构决定"）。
- **不做写操作。** 本文全部只读。
- **不 JOIN 明细表**（关键事实 2）。需要明细就是超出本文范围，另开任务书。
- **不改②的绑定机制本体**，只在其上新增一类分类，且 fail closed。
- **不碰审批机制**（`ApprovalGate` / `agent_approval_log` / `GATED_TOOLS`）。
- 不改 `calculator.rs` / `docfill.rs` / 测算引擎 / NPV / 现金流 / 税额 / 0 容差校验。
- 不为了"让模型多知道点"而放宽字段——多出来的每个字段都要挤占上下文。

## 验证要求

1. **真实链路**（带真实 key，不能只测函数）：
   问一个跨项目问题，确认模型确实调用了工具、返回值来自数据库而非模型编造。
2. **限权分类没有开后门**（对应"已定口径"的二维表，四格都要验）：
   - 绑定项目 A 的会话调用 `query_projects` → 放行（它在白名单里）
   - 同一会话调用 `run_benefit_calculation` 请求项目 B → **仍然拒绝**
   - **通用聊天会话**调用 `query_projects` → 放行
   - **通用聊天会话**调用 `run_benefit_calculation`（任意 projectId）→ **仍然拒绝**
   - 构造一个不在白名单、也不带 projectId 的工具调用 → **拒绝**（不能因为没 projectId 就放行）
3. **字段边界**：断言返回结构里**不出现**路径、`note`、`logs`，以及任何明细表字段。
4. **limit 上限**：构造超过上限的命中，确认返回"命中 N 条、仅返回 M 条"而不是静默截断。
5. **防混淆**：在绑定了项目 A 的会话里问"我这个项目毛利率多少"，
   确认模型答的是 A 的数字，没有被检索结果里其他项目串台。这条是本文的主要风险，
   **必须真人看一眼模型的实际回答**，不能只看工具返回值对不对。
6. `cargo test`、`cargo test agent_bridge -- --ignored`（真实 key）、
   前端 lint/build、插件 typecheck 全过。
7. 结果记入 `docs/verification/`，照实区分"已验证"与"未验证 / 已知限制"。

# 补充（2026-09-06）：返回值缺少甄选阶段口径，必须补上

> **本节是③交付后新增的缺口，由用户实测触发。** 优先级高于路线图 ④——
> 它不是体验问题，是**AI 报出的财务数字没有口径**，可能被填进错误的签批文件。

## 缘起

用户实测发现同一项目出现两组指标：NPV 65.64 / 利润率 8.63%，与 NPV 61.71 / 8.12%。

**排查结论：这不是数据漂移，两份都对**——它们分属**甄选前**与**甄选后**两个方案，
业务上前后都需要。`project_cashflow_states` 按 `(project_id, scheme_id)` 一方案一行，
`benefit_schemes.stage` 有 `pre_selection` / `post_selection` 标签，**存储结构是正确的**。

**真正的缺口在③的返回值。**

## 已确认的关键事实

### 1. `projects.summary_metrics` 只有一份，且语义是"最后保存的那个方案"

`project_state/mod.rs:1325` 的 `save_benefit_analysis` 在 `:1418` 把
`projects.summary_metrics` 改写成**本次保存的方案**的指标，同时把
`default_scheme_id` 指向该方案。

所以它永远等于"最后一次保存过的方案"的指标——是甄选前还是甄选后，
**取决于用户上一次动了哪张表**。语义确定，但**没有任何地方记录它属于哪个阶段**。

### 2. ③ 的 `ProjectRow` 把阶段维度整个丢了

`agent_bridge/project_query.rs:121-135` 返回：
`id`、`name`、`customerName`、`status`、`benefitStatus`、时间、金额、
`summaryMetrics`、`isBoundProject`——
**没有 stage，没有方案名，没有 `defaultSchemeId`，没有该方案的保存时间。**

### 3. ② 的测算工具反而是阶段感知的

`agent_bridge/calculation.rs:18-27`：`run_benefit_calculation` 的 `scenario` 参数
明确接受 `pre_selection` / `post_selection` / 方案 id / 方案名，`None` 时用默认方案。

**同一套工具面，②认识阶段而③不认识，这个不一致要消除。**

## 为什么必须修（不是锦上添花）

1. **甄选前后是两种口径，进不同的文档。** 甄选前是限价口径
   （三家询价最低价、最终不超过），甄选后是中标口径。
   立项签批表用前者，甄选结果签批表用后者。
   AI 说"这个项目毛利率 8.63%"却不说是哪个阶段，用户无法判断能不能直接用。
2. **跨项目汇总会静默失真。** ③ 把各项目的 `summaryMetrics` 放在一起排序、算合计。
   若 A 项目最后保存的是甄选前、B 项目是甄选后，**这个横向比较本身就没有意义**——
   而结果看起来完全正常，不会露馅。这是③"防混淆"目标的一个漏网场景：
   原先只防"跨项目串台"，没防"跨口径串台"。

## 要做的事

1. **`ProjectRow` 增加阶段信息**：至少包含该 `summaryMetrics` 对应的
   `stage`（`pre_selection` / `post_selection` / 未标注）、方案名、以及该方案的保存时间。
   数据现成：`projects.default_scheme_id` → `benefit_schemes.stage` / `name` / `updated_at`。
   > ⚠ 这需要 JOIN `benefit_schemes`。**它不违反本文"不 JOIN 明细表"的规则**——
   > 那条规则防的是科目、报价、供应商等**明细**进入返回值；
   > 阶段标签是**口径元数据**，恰恰是让数字可用的必要条件。
   > 但仍**只取 stage / name / updated_at 三个字段**，不带出方案的任何明细。
2. **工具结果里明示口径**，让模型能照实转述"（甄选后口径）"，而不是只报一个裸数字。
3. **汇总与排序要处理混合口径**：要么按 stage 分组给出，要么在结果里显式标注
   "本次结果包含不同甄选阶段的口径，不可直接横向比较"。
   **不要静默地把它们加在一起。**
4. **`stage` 为空（未标注方案）时要如实标"未标注"**，不要猜、不要默认当成甄选后。

## 不要做的事

- **不要为了"统一口径"去改 `save_benefit_analysis` 的写入语义**，
  也不要新增第二份 `summary_metrics`。存储结构是对的，缺的只是返回值上的标签。
- **不要让③自己重新测算**去补另一个阶段的数——③是只读汇总，重算是②的事。
- 不要借机放宽"不 JOIN 明细表"的总原则（第 1 条的例外范围已写死为三个字段）。
- 不改财务计算、税额、0 容差校验。

## 验证要求

1. 构造一个同时存在甄选前后方案的项目，确认返回值里的阶段标签与
   `default_scheme_id` 指向的方案一致；切换保存另一个阶段后再查，标签跟着变。
2. **混合口径的汇总**：A 项目甄选前、B 项目甄选后，确认结果按上面第 3 条处理，
   而不是直接给一个合计数。
3. `stage` 为空的方案，确认标为"未标注"而非被归入某一阶段。
4. **真人核对（与本文验证要求第 5 条合并做）**：绑定一个有甄选前后两套方案的项目，
   问"我这个项目毛利率多少"，确认模型答的数字**带口径说明**，
   而不是给一个来路不明的裸数字。
5. 回归：②的越权拒绝、③原有的字段边界与 limit 断言全部继续通过。
