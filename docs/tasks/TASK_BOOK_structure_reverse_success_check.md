# 任务书：智能结构反算未达目标却报"完成"并已写入金额

> **触发**：2026-09-10 D 轮开工核查——执行方在隔离测试中发现，
> 当指标只能取 9.4% 或 10.8% 时，**请求 10% 仍提示"结构反算完成"并调用金额写入**。
>
> 🔴 **这是桌面端今天就在犯的错，与 AI 无关，而且它会写钱。**
> D 件（反算卡片）在本书完成前不得开工——
> **给一个会假报成功的功能加 AI 入口，等于把错误放大一轮。**

## 根因：搜索结束后只校验"自洽"，从不校验"达标"

`useIctCalculations.ts` 的 `performLockedTotalStructureReverseCalculation`：

```js
// :944-958  二分搜索
for (let step = 0; step < 45; step++) {
  ...
  if (Math.abs(mid.metricValue - target) < Math.abs(best.metricValue - target)) best = mid;
  if (Math.abs(mid.metricValue - target) <= METRIC_EPSILON        // 命中
      || Math.abs(high.targetAmount - low.targetAmount) <= MONEY_EPSILON) {  // 区间塌缩
    best = mid; break;
  }
  ...
}
solutions.push({ targetAmount: best.targetAmount, point: best });   // ← 无条件收下

// :976-978
if (solutions.length === 0) return alert(":969 没找到可稳定收敛的区间");

// :980-984  按"改动最小"挑，不是按"最接近目标"挑
const bestSolution = solutions.reduce((best, current) =>
  Math.abs(current.targetAmount - structure.beforeTargetInclAmount)
    < Math.abs(best.targetAmount - structure.beforeTargetInclAmount) ? current : best, solutions[0]);

// :986-996  三道校验：可算 / 同侧总额不变 / 非负
//           ❌ 没有任何一道检查 finalPoint.metricValue 是否达到 target

state.updateTaxItemsInclBatch([...]);   // :990 直接写金额
```

**三道收尾校验保证的是"结果自洽"，不是"结果达标"。**
`solutions.length === 0` 只在**一个区间都没搜过**时触发；
只要搜过，哪怕最好的候选离目标很远，也会被收下、写入、报完成。

### 附带发现（执行方未提及）：区间塌缩时把"最好的"丢了

`:954` 的塌缩分支写的是 `best = mid; break;`——
**用最后一个中点覆盖了前面辛苦追踪的 `best`**，而 `mid` 未必比 `best` 更接近目标。
所以即便事后补上达标校验，**报出来的"当前值"也可能不是实际找到的最优解**。
修达标校验时**一并修这一处**。

## 现象：写在前，告知在后，而且标题说"完成"

`:1042-1049` 的成功提示**确实印了目标与当前值**：

```
结构反算完成：...
利润率：目标 10.00%，当前 9.40%
```

但三件事同时成立：

1. **标题是"结构反算完成"**——判定本身就是错的
2. **金额在 `:990` 就已经写进去了**，提示在 `:1042`——
   用户即使看出 10% ≠ 9.4%，**钱已经改完了**
3. → 对 AI 卡片路径更糟：模型会读到"完成"就转述成功。
   **上一轮已经证明模型会省略数字细节**（年度尾差），
   **不能指望它替用户发现目标与当前不一致。**

**可提炼的通则（建议写进 `AGENTS.md`）：**

> **`[min, max]` 区间检查只有在函数连续时才等价于"可达"。**
> 本项目的金额都按分取整、计划按年份对齐，**指标函数处处不连续**，
> 所以"目标落在范围内"**不能**推出"目标能达到"。
> **凡是搜索/求解，必须在收尾处显式校验"是否真的达到"，不能只校验"结果自洽"。**

## 要做的事

1. **收尾处新增达标校验**：`finalPoint.metricValue` 与 `target` 的差
   超出 `METRIC_EPSILON` 时**不得写入**，改为报错。
2. **错误必须带可达范围与实际最优值**：
   沿用 `:917 / :921 / :969` 的口径，告诉用户
   **"目标 10%，当前结构下最接近只能到 9.4%；可达范围 A–B"**——
   用户据此决定把目标改成多少。**只说"未达到"等于没答。**
3. **修 `:954` 的塌缩分支**：不要用 `mid` 覆盖 `best`，
   保留追踪到的最接近候选。
4. **候选挑选口径**：`:980` 按"改动最小"挑。**达标校验通过后**这条可以保留
   （改动最小是合理的业务偏好），但**不得在未达标时用它掩盖差距**。
5. **写入必须在校验之后**。保持"先判定、后写钱"的顺序。

## 不要做的事

- **不要放宽 `METRIC_EPSILON` 来让测试通过**。那是把"报错"换成"报错的数"。
- **不要在未达标时自动改写用户的目标值**（例如"已为你调整为 9.4%"）。
  达不到就是达不到，**改目标是用户的决定**。
- **不要动二分搜索本身的收敛策略、采样区间、`increasing` 判向**——
  本次只加收尾判定，不改搜索。
- **不要顺手启用 model_e 分支**（见下节）。
- 不改财务公式、税额、0 容差、资金计划同步。

## 附：为什么这条必须在 D 之前修

D 件要做的是"AI 提议目标 → 卡片 → 用户点击 → 调用既有反算"。
**既有反算现在会假报成功。**

若先做 D，用户在聊天里说"把利润率做到 12%"，卡片调用后拿到"完成"，
模型转述"已完成，利润率调整为 12%"——**而实际是 10.8%，钱已经改了**。
届时排查会先怀疑卡片、再怀疑模型，**最后才轮到这个藏了很久的判定缺口**。
