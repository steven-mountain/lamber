# 任务书：聊天内"生成文档"卡片（方案 B · AI 提示、用户点生成）

> **触发**：2026-09-07 用户实测——AI 能写字段了，但**无法生成 docx**。
> 产品界面点"立即生成文件"正常，只有 AI 这条路走不通。
>
> **这不是 bug，是缺一个入口。** 但**不给 AI 生成工具**，理由见关键事实 1。

## 已定方案：B（AI 提示 + 用户点击）

用户已在三个方案中选定 B：

| 方案 | 做法 | 为何不选 |
| --- | --- | --- |
| A | 把变量构造搬到后端，AI 直接调生成 | 719 行里嵌着测算、税额、甄选口径，风险高；且会产生**第二条生成链路** |
| **B** | **AI 判断"可生成"→ 聊天挂卡片 → 用户点 → 走原 `handleGenerate`** | **已选** |
| C | 维持现状，AI 完全不参与 | 用户无法判断"AI 说不能生成"是设计如此还是坏了 |

## 已确认的关键事实（写代码前不用重新调研）

### 1. `generate_lifecycle_docs` **不是自包含接口**，AI 直接调它会产出空壳文档

后端命令签名（`TemplateForms.tsx:2044-2051`）：

```js
invoke<string>('generate_lifecycle_docs', {
  moduleId, variables, selectedTemplates, outputDir, projectId, overwriteExisting })
```

**`variables` 要调用方先算好。** 算它的是前端 `handleGenerate`——
**`TemplateForms.tsx:1362-2081`，719 行，构造 121 个变量键**，其中包括：
保存态字段、测算指标格式化、科目明细拼接、税额口径、图片资产解析、
动态表格 JSON（`TABLE_TECH_ITEMS` / `TABLE_INQ_VENDORS`）、甄选批量模式校验。

→ 若给 AI 一个直接调后端的工具，它**调得到，但 `variables` 传空或传错**，
生成出一份空壳文档，**而且大概率不报错**。
这与本项目已修的模板 FormData 缺陷是同一种形状：**读不到就用默认值，静默出错**。

### 2. 不能有第二条生成链路

① 修完 FormData 后，四张模板"从字段所在页生成"与"从确认页生成"的产物一致性
已逐字段验过。若新开一条 AI 生成链路，就要**永远保证两条链路算出的 121 个变量完全一致**
——这正是本项目已经栽过跟头的形状（模板漂移、桥接契约两边各写一份）。

**方案 B 复用同一条链路，结构上不可能出现"AI 生成的和界面生成的不一样"。**

### 3. 已有可直接照搬的先例：图片上传卡片

`DemandImageCompletionCard.tsx` + `AiChatPanel.tsx` 的 `uploadTargets` 机制
就是"AI 提示 → 卡片 → 用户点击 → 走产品既有命令"。
**本次照这个模式做，不要另起一套。**

⚠ 并且**必须吸取它刚踩过的教训**（本任务书前身"补充二"）：
卡片触发**不要绑在 `templateDetail` 是否在 AI 上下文里**——
那会导致"不打开模板页就不出卡片"。**按绑定项目直接判断。**

### 4. 缺项判断已有共享纯函数，不要另写

`read_template_fields` 的 `getCatalogCompletion`（`readTemplateFields.ts:34`）
返回 `completion` / `missingFields`，条目含 `kind` / `evaluated` / `filled`。
**"这张表是否可以生成了"应当由它派生**，不要在前端再写一套判断。

⚠ 注意 `evaluated=false` 的项（如动态默认值未定、需外部方案计算的 check 项）
计入 `unknownCount`——**有未知项时不能声称"已齐备"**，卡片文案要如实反映。

## 要做的事

1. **新增"生成文档"卡片**，模式照搬图片卡片：
   - 触发：**按当前会话绑定的项目**判断，不依赖模板页是否打开（关键事实 3 的教训）
   - 展示：目标模板、当前完成度、**仍缺哪些项**（含 `unknownCount` 的如实说明）
   - 点击后**调用产品既有的 `handleGenerate` 路径**，不新写生成逻辑
2. **让模型知道这条路径存在**：工具/系统提示里说明"文档生成由用户在聊天卡片中点击完成"，
   避免它继续回答"我无法生成文件"而不给出路。
   > 但仍要如实说明**模型自己不生成文件**——它只提示，点击权在用户。
3. **缺项未齐时也要能出卡片**，但明确标注还缺什么、并允许用户仍然生成
   （与产品界面行为一致：界面并不强制齐备才让生成）。
   **不要自作主张地在缺项时禁止生成**——那会改变现有产品行为。
4. **生成结果要回执到聊天**：成功时告知产物路径（沿用图片卡片回执的口径，
   如实说明实际落盘位置），失败时把产品原本的错误如实带回，不要吞掉。

## 不要做的事

- **不要给 AI 一个直接调 `generate_lifecycle_docs` 的工具**（关键事实 1）。
- **不要把 `handleGenerate` 的变量构造搬到后端**，也不要在插件或 Rust 侧
  复制其中任何一段——那是方案 A，本次明确不做。
- **不要新增第二条生成链路**（关键事实 2）。卡片必须走产品既有路径。
- **不要把卡片触发绑在 `templateDetail` / 页面上下文上**（关键事实 3 的教训）。
- **不要在前端另写"是否可生成"的判断**，复用 `getCatalogCompletion`（关键事实 4）。
- 不改 `docfill.rs`、模板变量映射、Word/Excel 生成引擎。
- 不改 `handleGenerate` 的既有行为与校验（包括甄选批量那几条 `alert` 阻断）。
- 不改财务计算、税额、0 容差校验。
- 不碰审批机制——生成不是写业务数据，**不需要审批弹窗**；
  用户点击卡片本身就是确认。

## 验证要求

1. **原始场景**：绑定项目、**不打开模板页**，在聊天里说"帮我生成需求导入表"，
   确认卡片出现、点击后 docx 真的生成到项目目录。
2. **产物一致性（最重要）**：同一项目同一状态下，
   **卡片生成的 docx 与在产品界面点"立即生成文件"生成的 docx，正文逐字段一致**。
   这是"没有第二条链路"的证据，必须实际比对，不能只看两边都成功。
3. **缺项场景**：故意留一个缺项，确认卡片如实标注还缺什么，且仍可生成
   （与界面行为一致），生成的文档与界面同状态下生成的一致。
4. **`unknownCount` > 0 时**，确认卡片不声称"已齐备"。
5. **模型口径**：确认它不再说"我无法生成文件"就完事，而是引导用户使用卡片；
   同时仍如实说明自己不直接生成。
6. **未绑定项目 / 通用聊天**：确认不出现该卡片。
7. **失败路径**：构造一次生成失败（如附件图片文件缺失），
   确认产品原本的错误信息如实回到聊天，**不被吞成一句笼统的"生成失败"**。
8. 前端 lint/build、相关回归、插件 typecheck 通过；结果记入 `docs/verification/`。
