## 正确的费率表（基数 = 中选总金额**不含税**）

| 中选金额（不含税） | 服务费（不含税） |
| --- | --- |
| ≤ 1.21 万（12100） | **100.00 元** |
| （1.21 万, 4.85 万）开区间 | **× 0.825%** |
| [4.85 万, 10 万]（48500–100000） | **400.00 元** |
| （10 万, 100 万]（100000–1000000） | **× 0.809985%** |
| > 100 万 | **8099.85 元 / 项目**（定额） |

**实际按含税收取：含税服务费 = 不含税服务费 × (1 + 6%)。**

> 自洽性验证：1000000 × 0.809985% = **8099.85**，正好等于定额档
> → 0.809985% 与 100 万上界都读对了，费率表在 100 万处连续。

## 已确认的关键事实

### 1. 五处不符，逐条列清

`src-tauri/src/benefit/calculator.rs:372-402`（正算）与 `:406-452`（反算）：

| # | 位置 | 现状 | 应为 |
| --- | --- | --- | --- |
| 1 | `:388` | 上界 `<= 500000.0`（50 万） | **100 万** |
| 2 | `:389` | 费率 `0.009408`（0.9408%） | **`0.00809985`** |
| 3 | `:390-392` | `> 500000` 返回 **0.0** | **8099.85 定额** |
| 4 | `:384-392` | 直接拿传入值查档位 | **先换算成不含税再查** |
| 5 | `:386` | `<= 48500` 走费率 → 48500 时得 400.125 | **48500 归 400 元档** |

**`0.9408%` 在资费表里根本不存在，来源不明。**
本书初稿曾把"> 50 万返回 0"列为"待确认口径"——**已确认是 bug**。

### 2. 实际金额偏差

按**不含税**中选金额计（含税报价需先除以 1+税率 再对照本表）：

| 中选金额（不含税） | 现在算出 | 应为（不含税） | 偏差 |
| --- | --- | --- | --- |
| 30 万 | 2822.40 | 2429.96 | **多收 392.44** |
| 50 万 | 4704.00 | 4049.93 | **多收 654.07** |
| 60 万 | **0.00** | 4859.91 | **少算 4859.91** |
| 200 万 | **0.00** | 8099.85 | **少算 8099.85** |

### 3. 修正后的完整算式（含税报价 30 万、浮动 0、税率 6% 走一遍）

```
不含税报价 = 300000 / 1.06            = 283018.8679
档位       = (10万, 100万] → ×0.809985%
服务费不含税 = 283018.8679 × 0.00809985 = 2292.41
服务费含税   = 2292.41 × 1.06            = 2429.95
甄选最高限价 = 300000 + 2429.95          = 302429.95   （含税）
```

> **算术更正（执行核查）**：原示例2292.42 / 2429.97 / 302429.97算错；原始服务费实际为2292.410377…，先不含税舍入再加税应得到2292.41 / 2429.95 / 302429.95。

⚠ **四舍五入的次序必须钉死并写进测试**，否则会出现 ±0.01 的口径争议。

### 4. 🔴 反算存在无解区间，今天被静默填了不存在的报价

资费表在 10 万处**跳变**：不含税 10 万整 → 400 元；10 万零 1 分 → 约 810 元。
换算到含税口径（6%）：

```
含税报价 106000.00  → 服务费含税 424.00   → 限价 106424.00
含税报价 106000.01  → 服务费含税 858.59   → 限价 106858.60
                                             ↑ 约 434.59 元宽的区间无解
```

> **算术更正（执行核查）**：原上界106858.59漏加了报价中的0.01，正确为106858.60。另有低档向下跳变形成多解；实现返回精确候选并说明选择，不承诺多解处唯一恢复原始报价。

**今天 `reverse_calculate_selection_fee:438-443` 会照样 `T / 1.009408`
算出一个报价并返回，不报错。它返回的是一个根本不存在的报价。**
→ 又一次"读不到就悄悄降级"，这次的产物是一个假金额。

### 5. 🔴 反算的边界必须由税率常量推导，不能再手写字面量

> **更正（2026-09-09 晚）**：本节初稿写的是"边界随税率变化，必须现场推导"。
> 用户随后确认**税率锁定 6%**，所以含税边界其实是**定值**。
> **但"不要手写字面量"这条结论不变**，理由见下。

现有常量 `12200` / `48900.12` / `100400` / `504704`（`:427-444`）
全部由旧费率手工推出并写死。**它们错了这么久没人发现，正是因为它们是手写的小数**
——`504704` 看上去和 `1008099.85` 一样"像个正经数字"，肉眼分辨不出哪个对。

锁定 6% 后的含税边界：

| 不含税档位边界 | 含税边界（×1.06） |
| --- | --- |
| 12100 | 12826.00 |
| 48500 | 51410.00 |
| 100000 | 106000.00 |
| 1000000 | 1060000.00 |

**要做的是：把不含税档位表和 6% 声明为唯一事实源，边界由代码算出来。**
不是因为税率会变，而是因为**手写的推导结果无法被审阅**。
下次资费表调整时，改一处表、边界自动跟着走。

### 6. 含税口径下写入侧要改的只有服务费那一笔

`useIctCalculations.ts:487-550` 的 `applySelectionLimit`：

```
targetIncl     = 限价 − 服务费     （selectionFee.ts:80）
serviceFeeIncl = 服务费（原样）     （selectionFee.ts:81）
updateTaxItemsInclBatch([{incl: targetIncl}, {incl: serviceFeeIncl}])
```

既然**限价是含税的**，`targetIncl` 当含税写入**本来就是对的**。
问题在于减掉的 `selFee` 是**不含税**服务费 → 目标科目**多算**了服务费的税额，
中标服务费科目**少算**了自己的税。**两处的差都是那 6%。**

> `SELECTION_FEE_SERVICE_SUBJECT_CODE = "cost_it_bidding"`（`selectionFee.ts:8`）。

### 6b. 🔴 "目标科目只能 6%"会挡掉 19 个成本科目里的 8 个

用户已确认目标投入科目**必须是 6% 税率**。实际影响面（`ictSubjectCatalog.ts:53-71`）：

**可选（6%，10 个）**：勘察设计/预备费、**集成服务**（默认目标）、其他投入、维护费用、
设计院成本评估费、第三方审计评估费、其他产品成本、融合营销成本、渠道酬金、其他管理费用等

**被挡（8 个）**：
`cost_it_device` **主要设备/甲供材料 13%**、`cost_it_construction` **施工 9%**、
`cost_it_running` 其他运行支出 13%、`cost_ct_construction` 专线建设 9%、
`cost_ct_maintenance` 专线维护 9%、`cost_ct_bandwidth` 专线带宽 9%、
`cost_ct_renewal` 专线/其他产品续签 9%、`cost_non_it_ct` 工程施工投入等 9%

默认目标 `cost_it_integration`（6%）不受影响。

⚠ **两个必须注意的点：**

1. **按科目的"当前实际税率"判定，不是 `defaultTaxRate`。**
   用户可以在界面上改单个科目的税率（`restoreItem` 同时读 `tax_rate` 与
   `defaultTaxRate`）。若只查定义里的默认值，一个被改成 9% 的集成服务会被放过。
2. **已保存项目可能用了非 6% 的目标科目。** 重新写入时会被拦截——
   这是对的，但**错误必须说清是历史选择导致的**，
   不能只丢一句"科目不合法"让用户以为是新 bug。

### 7. 合并写入模式今天不存在

`applySelectionLimit` **无条件写两笔**。用户说明真实业务里
"有时候把中标服务费加进集成费或其他科目，不单独拆分甄选服务费"。
→ **这是新功能，不是口径修正**，但与本次同属一处代码，一起做。

### 8. 两个函数今天零测试

`calculator.rs` 的 `mod tests`（`:457` 起）**无一条覆盖这两个函数**，已全文检索确认。
**这是错了这么久没被发现的直接原因。**

## 要做的事

1. **正算改正五处**（关键事实 1），含 48500 / 100000 两个临界归 400 元档。
2. **档位查找先换算**：入参按含税处理，**除以 1.06** 后再对照费率表。
   报价、限价、浮动**三栏统一按含税**。
3. **返回值同时给出不含税与含税服务费**，不要只给一个数。
4. **反算边界由"不含税档位表 + 6%"推导**（关键事实 5），
   禁止手写 `1008099.85` 这类字面量。
5. **无解区间返回明确错误**（关键事实 4），文案说清
   "该限价落在资费表 10 万元档位跳变形成的空档，无对应报价"。
   **禁止返回近似值。**
6. **写入侧改服务费那一笔**（关键事实 6）：用含税服务费参与相减与写入。
   **复用既有 `normalizeTaxPairFromIncl` 财务口径检查**，不要绕过。
7. **新增"合并写入"开关**（关键事实 7）：
   - 默认**拆分**（保持现有行为）
   - 勾选后：目标科目写**全额限价**，**不写**中标服务费科目
   - 选择**随方案持久化**（`IctInput` 已有 `selection_fee_*` 字段可扩展，
     `models.rs:105-118`），否则重开界面会悄悄变回默认
7b. **目标科目限定 6%**（关键事实 6b）：
    按**当前实际税率**判定，非 6% 时**明确拦截并说明原因**
    （如"甄选限价目标科目须为 6% 税率，主要设备/甲供材料为 13%"），
    **科目仍留在下拉里可见，不要静默移除**。
    历史项目命中此拦截时，文案要点明是既有选择导致，不是新故障。

8. **界面标注税基**：报价、限价、浮动三栏统一标注"（含税）"。
9. **补测试**（关键事实 8），至少覆盖：
   - 五个档位各取中间值
   - 六个临界：12100 / 12100.01 / 48500 / 100000 / 100000.01 / 1000000 / 1000000.01
   - 含税换算：含税报价 → 不含税查档 → 含税服务费
   - **无解区间明确报错，不返回数字**
   - 正反算互逆（无解区间除外）
   - **把税率常量临时改成 9%，确认四个边界跟着变**，防止字面量复活
   - 拆分 / 合并两种写入模式各一条
   - **非 6% 目标科目被拦截**，且科目仍在下拉中可见
   - **被手工改成 9% 的 6% 科目也要被拦截**（按当前税率而非默认值判定）
10. **不再吞错误**（关键事实 9），把失败呈现到界面。

> **开工前的两个待确认项已于 2026-09-09 晚由用户答复，均已并入上表与关键事实 6b：**

## 不要做的事

- **不要在修完之前把甄选费接给 AI**（AI 任务书 C 件依赖本书）。
- **不要只改费率不改含税**（或反之）。分开上线会产生一个"改了一半"的版本，
  比现在更难判断哪些历史数据是对的。
- **不要在无解区间返回"最接近的"报价**——返近似值只是把静默降级换个说法。
- **不要把新的档位边界写死成常量**（关键事实 5）。
- **不要顺手改 `applySelectionLimit` 的科目选择、批量提交、付款计划同步**，
  本次只动金额口径与拆分开关。
- **不要自动重算历史项目的存量数字**——见下节，改的是算法不是数据。
- 不改财务公式、0 容差校验、`normalizeTaxPairFromIncl` 本身。
- 不改询价"一键生成三家报价"（那是另一条链路）。

## 历史项目：按最新算法，但要如实告知

用户已决定**按最新的来**，理由是真实项目没有超过 10 万的，超 10 万的都是测试项目。

⚠ **但"真实项目不受影响"并不成立**，含税修正（关键事实 6）会改动**定额档**：

| 档位 | 旧写入值 | 新写入值 |
| --- | --- | --- |
| 100 元档（定额） | 100.00 | **106.00** |
| 400 元档（定额） | 400.00 | **424.00** |
| **比例档**（1.21–4.85 万、10–100 万） | — | **金额不变** |

> **更正（2026-09-09 执行后）**：本表初稿写"比例档 247.50 → 262.35"，**是错的**。
> 比例档现在是 `报价 ÷ 1.06 × 费率 × 1.06`，**除税与加税恰好抵消**，
> 结果等于旧的 `报价 × 费率`。变的只是**语义**（过去把不含税值当含税写入，
> 现在它真的是含税值），金额不动。
> 定额档没有这个抵消，所以只有它们变。执行方在验证记录中指出了这一点。

金额不大，但**定额档的已保存项目重新打开后数字会变**。
→ **不做数据迁移**（算法变，存量输入不动，重算即得新值），
但**变更说明里要写清这一点**，否则用户会以为是新 bug。

## 验证要求

1. **逐档对照**：五个档位与六个临界点，与资费表**手工逐一核对**。

8. **开关持久化**：勾选合并 → 保存 → 重开方案，仍是合并。
9. **历史项目对照**：任取一个已保存的真实项目（≤10 万档），

## 附：为什么这五处能潜伏这么久

**因为这两个函数一条测试都没有**（关键事实 8），
而且失败还被吞进 console（关键事实 9）。

费率表是外部规则，会变；本次补的测试**必须把资费表的档位与费率作为断言写死**，
这样下次资费表调整时，是**测试先红**，而不是**用户先算错**。
