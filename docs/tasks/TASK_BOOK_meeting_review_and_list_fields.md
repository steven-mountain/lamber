> **触发**：2026-09-07 用户连撞两次"清单类字段 AI 改不了"，
> 排查时发现**会审纪要根本没进 `catalog.json`**。
>
> **2026-09-08 方案定稿**：两张清单都做，但**做法完全不同**——
> `techItems` 走"AI 提议 → 卡片编辑"，`inqVendors` 走"AI 提示 → 确认 → 触发既有生成器"。

> **执行进度（2026-09-08）**：第〇至四件开发及自动/桌面验证完成；锁屏后已补齐回执真实模型复测、未绑定/通用卡片隐藏验证。真人及旧版Word留样比对不冒充完成。详见 [验证记录](../verification/meeting-review-and-list-fields.md)。

## 已确认的关键事实（写代码前不用重新调研）

### 1. 会审纪要是唯一没进目录的模板

`catalog.json` 现有六个模板条目：demand / approval / selection 有字段，
presales / benefit / decision 是显式排除的空表。**没有 meeting。**
它的完成度仍写死在 `TemplateForms.tsx:2141-2171` 的 `meetingCompletionItems`（**29 项**），
而另外三张已改用 `getCatalogCompletion`。

29 项按性质分类（**必须人工逐条确认**，见关键事实 4）：

> **⚠ 下面这份分类的数字已被 2026-09-08 核查修正，以关键事实 7 为准**
> （18 个可写文本 key / 17 个完成度项 / 10 个只读或复合项 / 2 个清单项）。
> 保留原文是为了让"当初怎么估的"可追溯。

- **纯文本、可写**（原估约 17，实为 18 个 key 占 17 项）：会议方式、技术方案、三化方案、战略价值、综论、时间要求、
  风险点及其他责任人、售中建设及施工界面、单一来源说明、项目评审清单准确完整、
  是否联合体投标、驻点支撑人员、分公司参会人员……
- **派生**（约 6）：项目背景、IT/CT 建设内容、收入付款方式、支出付款方式、资金来源
- **条件必填**（约 4）：市公司参会人员（`projectScale === "large"` 才必填）、
  中台能力调用、采购方式其他、是否涉及单一来源
- **清单**（2）：技术方案可行性清单、询价情况/询价过程

### 2. ⚠ 两张清单本质不同，做法必须不同

| | `techItems`（需求表 + 会审纪要） | `inqVendors`（会审纪要） |
| --- | --- | --- |
| 行结构 | `{serviceName, serviceDesc, amount, unit}` | `{vendorName, amount, taxRate, remark, images}` |
| `amount` 含义 | **数量**——`:1620` 映射到 `TECH_ITEM_QTY`，默认 `1 套` | **金额**（含税报价），另有 `taxRate` |
| 是否进计算 | **否**，纯渲染进 docx | **是**——`:1532` 按 amount 过滤，`:1150` 进上下文 |
| 内容来源 | 用户自由描述 | **从 IT 成本推导、收入封顶**（见关键事实 3） |
| 附带 | 无 | 报价**截图**＝询价证据 |
| 已有生成器 | 无 | **"一键生成三家报价"** |
| **本次做法** | **AI 提议行内容 → 卡片编辑** | **AI 只提示与触发，不碰内容** |

**下一个看到 catalog 里两个 `kind: "list"` 的人几乎必然想"一起支持"。不行——
一个是让 AI 提议内容，另一个是让 AI 按一下按钮。**

### 3. `inqVendors` 的金额是推导出来的，产品已有合规生成器

`autoGenerateInquiry`（`TemplateForms.tsx:1242-1273`）：

```js
const limit = IT 投入含税总成本（10 个科目相加）        // 底价硬性绑定成本
if (limit === 0)               拒绝  // "三家报价的底价需硬性绑定成本"
if (totalRevenueIncl <= 0)     拒绝  // "最高价不能超过含税总收入"
if (limit > totalRevenueIncl)  拒绝  // "无法生成合规三家报价"

const quotes = [ limit,
  Math.min(totalRevenueIncl, round(limit * (1.05 + random()*0.02))),
  Math.min(totalRevenueIncl, round(limit * (1.10 + random()*0.05))) ].sort()

// 产出：厂商A/B/C、三档报价、taxRate 6、最低价标"最低"、每行 images: []
```

且 `:1237` 连**手工输入**都封顶：`Math.min(numeric, totalRevenueIncl)`。

→ **这些约束由生成器自己保证。AI 触发它，改变不了任何一条。**
→ 生成后每行自带空的 `images` 槽（`:1268-1271`），**上传位置自然出现**。

> **⚠ 生成结果带随机性**：报价浮动用了 `Math.random()`，厂商顺序还 `shuffled` 打乱。
> **所以卡片不能先"预览"再确认**——预览的数字和真正生成的对不上。
> 必须是"确认 → 生成 → 展示实际结果 → 用户改"。

### 4. 完成度清单里混着派生与条件必填，不能当字段目录用

这是字段目录泛化那份任务书已确立的原则，**会审纪要是最严重的一张**：
29 项里只有约 17 项是可写文本，且"市公司参会人员"这类带条件
（`projectScale !== "large" || ...`），对应目录的 `requiredWhen`。

### 5. `techItems` 是两张表共用同一份数据

`TemplateForms.tsx:244` 只声明一次，渲染于 `:2458`（会审纪要页）
与 `:3449`（需求导入表页，标签为"技术方案可行性清单 (设备需求清单)"）。
**改它会同时影响两张表。**

### 6. ⚠ 判据已修正（2026-09-08 开工核查后）：是"零 meeting 专用代码"，不是"零代码"

> **原文写的是"应零代码改动，必须改代码就停下来汇报"。GPT 照做并停了，停得对。**
> 核查记录：`docs/verification/meeting-review-catalog-preflight.md`。
> 核查发现的是**通用目录契约的能力缺口**，不是会审纪要的特例。**已批准先补契约。**

字段目录泛化曾通过"第三模板判据"（加甄选结果签批表时 240 个源码哈希不变），
但那张表恰好没用到条件必填与复合计数，所以没暴露下面四个缺口：

1. **`requiredWhen` 只做 `Boolean(state[key])`**（`catalog.ts`）。
   而 `projectScale` 是字符串——`"large"` 与其他非空值**都为 true**；
   `procurementMethod` 的 `"其他"` 与 `"短名单甄选"` 同样。
   → **无法表达"仅当等于某值时必填"。这对任何模板都成立，会审纪要只是第一个撞上的。**
2. **Rust 侧 `template_read.rs` 用 `Value::as_bool` 投影条件**，字符串一律 `false`。
   → **页面与聊天两条路径口径相反**；只在页面补临时布尔值会造成两套完成度。
3. **一个完成度项对应多个字段**："分公司参会人员" = `gen_branch_name` **且**
   `gen_branch_attendees`。现有算法一字段一计数项。
4. **清单有效行判断**：原询价项要求"至少一行有厂商名或正金额"，
   目录 `list` 只判数组非空 → **空白行在两条路径结果不同**。

另：Rust `Field` 启用 `deny_unknown_fields`，构建脚本只接受五种既有 `kind`，
**第四件的 `list.editable` 这类写法也做不到**——需保留 `kind: "list"`，
另加经校验的子类元数据。

**修正后的判据：**

> **零 meeting 专用代码。** 补齐通用目录能力**是允许的**——它服务所有模板；
> 但**不得出现 `if (template === 'meeting')` 这类模板特例分支**。
> 判据的实质从未变过：**加模板不该写模板专用代码。**

⚠ **不得用 `completionValues` 绕过。** 它能让页面传外部事实，但读工具不生成这些值——
用它覆盖只会让**页面看起来通过而聊天仍然错**，那正是缺口 2 的表现，不是修复。

### 7. 实际字段数：18 个可写文本 key，占 17 个完成度项

原文写的"约 17 项"不精确。核查确认：**18 个可写文本 key**
（"分公司参会人员"含两个），对应 **17 个完成度项**；另有 10 个只读/复合项、2 个清单项。
**字段目录条目数与完成度计数可以不同**——这正是缺口 3 要支持的。
页面仍须保持原 **29 项及原顺序**。

## 要做的事

### 〇、补齐通用目录契约能力（2026-09-08 新增，第一件的前置）

> **这件事是被核查逼出来的，不在原计划里。** 它必须**先于**第一件完成，
> 且**必须做成通用能力**——四个缺口对任何模板都成立，会审纪要只是第一个撞上的。

0.1 **条件必填支持声明式相等判断**：`requiredWhen` 从"根状态键取布尔"
    扩展为可表达 `{ field, equals }` 一类的显式条件。
    **旧写法必须继续有效**（三张现有模板不许改 JSON）。

0.2 **`template_read.rs` 用同一套语义投影条件**，不再 `Value::as_bool`。
    → 缺口 2 是这批改动里**最要紧的一条**：页面与聊天必须同口径。

0.3 **一个完成度项可由多个字段共同决定**（缺口 3）。
    目录条目数与完成度计数解耦。

0.4 **清单可声明"有效行"判据**（缺口 4），使"至少一行有厂商名或正金额"
    能在两条路径得到相同结论，而不是各判各的。

0.5 **`kind` 保持既有五种**，第四件的清单子类用**另加的、经构建期校验的元数据**表达
    （Rust `Field` 有 `deny_unknown_fields`，构建脚本白名单同样限制）。

0.6 **外部事实缺失时记 `unknown`，不得默认判过。** 这是既有约定，改动中不得放宽。

**硬约束（违反即返工）：**

- **通用，不得出现模板特例分支。** 没有 `if (template === 'meeting')`。
- **页面与读工具共用同一个完成度函数**，不许在任何一侧另写一份。
- **不得用 `completionValues` 覆盖来充当修复**（关键事实 6）。
- **三张现有模板（需求表 / 立项签批表 / 甄选结果签批表）的完成度数字、
  缺项清单、条目顺序逐项不变。** 这三张是回归基线，`catalog.ts` /
  `template_catalog.rs` / `template_read.rs` 是字段目录泛化那轮刚稳定的代码。

### 一、会审纪要文本字段进目录

1. `catalog.json` 新增 `meeting` 条目，**逐条人工分类** 29 项，带条件必填。
2. `meetingCompletionItems` 改为调用 `getCatalogCompletion`，与另外三张一致。
3. **判据（已修正）：零 meeting 专用代码**——第〇件补的是通用契约，
   第一件本身除第 2 条那处替换外不得再改代码（关键事实 6）。

### 二、`techItems` 特化卡片

4. 一张**可编辑表格卡片**，列固定（服务名称 / 服务描述 / 数量 / 单位，
   目录已声明 `columns`），行可增删改。
   **AI 提议行内容**（它读得到项目背景与服务内容），用户核对、修改、点保存。
5. **⚠ 卡片顶部明示"此清单同时用于需求导入表与会审纪要"**（关键事实 5）。
   不写这句，用户以为只改了需求表——**又一次跨模板的静默影响**。
6. **不需要审批弹窗、不需要行级 diff、不需要新写工具契约**：
   卡片本身就是那个界面，**所见即所得**，"少传一行=静默删除"的风险不存在。
   写入由用户点击触发，符合 `AGENTS.md`。先例：图片卡片同样不走审批。

### 三、`inqVendors` 询价卡片（AI 只提示与触发）

7. **AI 发现询价未填时提示**，聊天里挂一张确认卡片。
   卡片上说清将要做什么：按 IT 投入成本生成三家报价，最高价不超过含税总收入。
8. **用户点确认 → 调用既有 `autoGenerateInquiry`**，不复制、不重写它的任何一行逻辑。
9. **生成后在卡片里展示实际产出的三行**（厂商名/报价/税率/备注）
   **＋ 每行一个图片上传位**，用户改厂商名、传报价截图。
   > 因关键事实 3 的随机性，**不做生成前预览**。
10. **三条前置校验失败时，把原始提示如实带回聊天**
    （如"IT 投入含税总成本已超过含税总收入，无法生成合规三家报价"），
    并引导用户**先去完善成本或收入**。
11. 卡片触发按**绑定项目**判断，不依赖模板页是否打开；通用聊天 / 未绑定不出现。

### 四、目录标注

12. 在 `catalog.json` 里把两张清单标成**不同的子类**（例如
    `list.editable` 与 `list.generated`），并写明各自的处理方式与理由。
    光标 `kind: "list"` 不够——那正是会让人一起支持的原因。

## 不要做的事

- **不要为了让第一件"看起来零代码"而绕开第〇件**：
  不许用 `completionValues` 覆盖、不许在页面侧临时塞布尔字段、
  不许只改页面不改 `template_read.rs`。**两套完成度口径比缺功能更糟。**
- **不要把通用契约做成会审纪要专用分支**（关键事实 6 的修正判据）。
- **不要在第〇件里顺手重构字段目录的其他部分**——它是刚稳定的代码，
  本次只补这四个缺口。
- **不要给 AI 写清单行的能力**——两张都不给。
  `techItems` 是"提议 + 用户在卡片里落笔"，`inqVendors` 是"提示 + 触发既有生成器"。
- **不要让 AI 参与 `inqVendors` 生成后的编辑**。用户改厂商名、改金额走**原有路径**
  （`updateInqVendorAmount`，仍有 `Math.min` 封顶）。
  AI **不得**提议"把厂商A的报价改成 X"——那就绕回"AI 写金额"了。
- **不要在三条前置校验失败时给绕过方案**（比如建议手工加三行）。
  如实转述、引导用户补数据，是唯一正确的行为。
- **不要复制或重写 `autoGenerateInquiry` 的推导逻辑**到卡片、插件或 Rust 侧——
  那会立刻产生第二条合规链路，与"不新增第二条生成链路"同理。
- **不要做生成前预览**（关键事实 3 的随机性）。
- **不要把两张清单做成同一个通用组件**再用配置区分——它们的交互语义不同，
  强行统一会让"AI 能不能提议内容"这条边界变模糊。
- 不改 `docfill.rs`、`TABLE_*` 行克隆机制、Word 生成引擎。
- 不改财务计算、税额、0 容差校验、甄选费逻辑。
- 不碰两张清单在模板页上的既有编辑功能。

9. **约束仍然生效**：构造 `limit > totalRevenueIncl` 的项目，
   确认卡片**拒绝生成**并把原始提示带回聊天，且 AI **没有**给出绕过建议。
10. **封顶仍然生效**：生成后在卡片里手工把某行金额改成超过含税总收入的数，
    确认仍被 `Math.min` 封顶。
11. **AI 不碰内容**：确认模型在生成后**没有**提议具体的厂商名或报价数字。
12. 未绑定 / 通用聊天不出现卡片。

### 通用

13. 回归：②越权拒绝、③聚合放行、需求表原 8 文本、立项签批表与甄选结果签批表既有写入
    全部不受影响。
14. `cargo test`、真实 key 集成、前端 lint/build、插件 typecheck、打包检查全过。
15. 结果记入 `docs/verification/`，照实区分"已验证"与"未验证 / 已知限制"。

## 附：为什么 `inqVendors` 从"永久排除"改成"可以触发"

本文早先版本把它列为**永久排除**，理由四条：写它等于写金额与税率、它是甄选合规证据、
挂着模型不能写的图片、金额是受约束推导出来的。

**这四条至今全部成立**——但它们证明的是"**AI 不能写行**"，不是"这张表不能碰"。
用户 2026-09-08 提出的方案让 AI **只触发既有生成器**，四条约束仍由
`autoGenerateInquiry` 自己保证，AI 改变不了任何一条。

**保留这段是为了说明边界为什么移动**：移动的不是安全线，是 AI 的角色——
从写入者变成触发者。若将来有人想让 AI 直接写询价行，上面四条理由**依然有效**，
不要拿本次的放宽当先例。
