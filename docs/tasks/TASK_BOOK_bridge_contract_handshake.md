# 任务书：桥接契约握手——版本错配必须启动即失败，不能表现为逐次 404

> **执行状态（2026-09-06）**：实现与新版验证完成；严格旧版用户文案仍有已验证限制，不能整体勾选通过。见 [验收记录](../verification/bridge-contract-handshake.md)。

> **触发**：2026-09-06 用户实测 ③ 跨项目查询时，所有工具读取被
> `lamber bridge /lamber-bridge/authorize → 404 未知的 AI 桥接路由` 拦住。
> 模型把它转述成"数据访问通道返回错误"，用户无法判断这是 bug、是没连上、还是版本不匹配。
>
> **优先级**：建议插在路线图 ④ 之前。它不阻塞 ④⑤⑥ 的设计，但每多一个工具，
> 错配时的表现就多一处不可解释的失败。

## 症状与现场

- 每次工具调用返回 404，错误文案是给开发者看的路由名，不是给用户看的话。
- 模型行为本身是**对的**：拒绝编数字、如实说读不到、贴出原始错误——不要去"修"模型。
- 要修的是：**这种失败不该以逐次调用 404 的形式渗出来**，应该在启动时一次性说清楚。

## 已确认的关键事实（写代码前不用重新调研）

### 1. 当前源码的路由是对的，不是路由 bug

- `AUTHORIZE_ROUTE = "/lamber-bridge/authorize"`（`agent_bridge/project_bindings.rs:5`）
- 生产 dispatcher `workspace_handler`（`agent_bridge/mod.rs:151-153`）放行
  `CALCULATE_ROUTE` / `AUTHORIZE_ROUTE` / `QUERY_ROUTE`，其余才返回
  `BridgeReply::error(404, "未知的 AI 桥接路由")`（`:155`）
- 两个 handler 的组合也正确：`streaming::handler(fallback = workspace_handler(...))`
  （`mod.rs:445-446`），非 stream 路径正确下沉（`streaming.rs:97-99`）

**所以最新代码不会对 `/authorize` 返回 404。出现 404 只可能是运行中的 Rust 二进制比插件旧。**

### 2. 插件每次启动都会刷新，但**没有任何机制保证 Rust 二进制与之匹配**

`distribution.rs:160-162` 注释原文：

> The plugin is application code, not user state. Refresh it on every dsh
> launch so an app upgrade cannot keep executing an older copied plugin.

所以插件相对**应用资源**永远是新的——同一个 app 包内不会漂移。
但它保证不了**运行中的 Rust 二进制**和插件同代。

### 3. 漂移窗口在开发模式

`lamber_plugin` 在开发布局下指向仓库的 `agent-bridge/dsh-tool-lamber`，刷新时复制
`package.json` + `lib/`（编译产物）。于是：

**只要 `lib/` 被重新构建、而 Rust 二进制没有重新构建**（跑的是旧的 `target/debug` 产物，
或先前构建的 dev `.app`），就会出现"新插件打旧二进制"。
阶段 3A 的打包文档已有一句相关提醒——"Always rebuild the plugin before preparing
resources"——说明两者的构建本来就是分开的两步，靠人记住。

### 4. 桥接两侧没有版本或能力协商

`dsh-tool-lamber/src/bridge.ts` 只约定三个环境变量：
`LAMBER_BRIDGE_URL`、`LAMBER_BRIDGE_TOKEN`、`LAMBER_BRIDGE_TOKEN_HEADER`。
**没有版本号，没有能力清单，没有启动时的一次性校验。**

### 5. 这是"读不到就悄悄降级"的同一族问题

本项目已经踩过三次同族的坑，都被记录在案：模板 FormData 静默用默认值、
装机版模板目录不存在时静默返回空数组、以及本条。
共同点是**失败没有信号，或信号只对开发者可读**。修法也一致：**让它在最早的时刻大声失败**。

## 要做的事

1. **新增契约握手**：插件在注册工具之前（`apply(ctx)` 内，早于任何工具可被调用的时刻）
   向 Rust 报告自己的**契约版本**与**所需路由集合**。
2. **Rust 侧比对，不匹配就让启动失败**——不是记一条 warning 然后继续。
   失败要沿用现有的启动失败通道（参照 `distribution.rs` 缺件时那套），不要新造。
3. **错误文案必须是给用户看的人话，且能区分三种情况**：
   - 桥接不可达（进程/端口/令牌问题）
   - **版本错配**（本次要解决的）——文案要能引导用户重新构建或重装，
     不要出现路由名、404、`workspace_handler` 这类开发者词汇
   - 业务错误（权限拒绝、项目不存在等）——这类保持现状，不要被握手改动波及
4. **契约版本要有单一权威来源。** 两边各写一个常量早晚会漂——这正是本文要修的病，
   不要用同样的形状去修它。可以由构建步骤生成，或由 Rust 侧作为唯一来源、插件从环境变量读取。
   选哪种要在 `agent-bridge/README.md` 写明理由。
5. **补一条构建期防呆**：`npm run test:packaging` 或等价位置加断言，
   确保打包出的插件 `lib/` 与随包 Rust 二进制的契约版本一致。
   关键事实 3 说明这一步现在靠人记住，靠不住。

## 不要做的事

- **不要用重试、退避或"失败就跳过工具"来掩盖错配。** 错配不是瞬态故障，重试只会拖长困惑。
- **不要把 404 改成 200 空响应**，那会让模型拿到"查到了但没数据"，比报错更糟——
  它可能据此说"该项目没有毛利率数据"，而事实是根本没查成。
- **不要改任何现有路由的语义、路径或 404 行为本身**。未知路由继续 404 是对的；
  本文加的是**启动时的握手**，不是改运行时的分发。
- 不碰审批机制（`ApprovalGate` / `agent_approval_log` / `GATED_TOOLS`）。
- 不碰 ②的项目限权与 ③的聚合只读分类——握手在它们之前发生，不参与鉴权判断。
- 不改 `calculator.rs` / `docfill.rs` / 测算引擎 / 财务逻辑。
- 不新增依赖。
- **不要顺手去"修"模型的措辞。** 模型如实报错是正确行为，问题在它拿到的错误本身。

## 验证要求

1. **构造错配**：故意让插件声明一条 Rust 不认识的路由（或把契约版本调高一格），
   确认**启动阶段**就失败，且用户看到的是人话文案，不是 404 或路由名。
2. **正常路径不受影响**：版本一致时握手静默通过，工具调用行为与现在完全相同；
   ②的越权拒绝、③的聚合放行、审批四条路径全部回归通过。
3. **三类错误可区分**：分别构造"桥接不可达""版本错配""业务权限拒绝"，
   确认三者的用户可见文案互不相同，且都不含开发者词汇。
4. **构建期防呆**（要做的事第 5 条）单独验一次：制造插件与二进制不同代的构建，
   确认打包步骤失败而不是产出一个装上去才发现问题的包。
5. 复现本次现场：用旧二进制 + 新插件跑一次，确认现在得到的是启动期的明确提示，
   而不是模型转述的"数据访问通道返回错误"。
6. `cargo test`、`cargo test agent_bridge -- --ignored`（真实 key）、
   前端 lint/build、插件 typecheck、`npm run test:packaging` 全过。
7. 结果记入 `docs/verification/`，照实区分"已验证"与"未验证 / 已知限制"。

## 顺带

修完之后，③ 的**真人防混淆核对仍未完成**——用户上次就是被这个 404 挡住的。
重新构建后需要再问一次**裸问题**（"我这个项目毛利率多少"，不加"只引用已保存汇总/请明确项目名"
这类引导），确认模型仍答当前绑定项目而不是检索结果里的其他项目。
详见 `TASK_BOOK_cross_project_query.md` 验证要求第 5 条。
