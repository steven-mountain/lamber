# 任务书：AI 写入模板字段（含审批弹窗升级）

> **位置**：路线图 [ROADMAP_ai_capabilities.md](./ROADMAP_ai_capabilities.md) 第 ④ 项，
> 但**把第 ⑤ 项（参数二次确认）提到了它前面**，理由见下。
> 前置 ①②③ 已完成，桥接握手已修。
>
> **这是本项目第一个真正写业务数据的工具。**

## 为什么把 ⑤ 提到 ④ 前面（路线图修订）

原路线图把"参数二次确认"排在 ⑥（建项目/改测算参数）之前、④ 之后，理由是
④ 只写文本、不写数字。**这个判断不对，要改。** 两条理由：

### 1. 看不懂的东西点确认，不叫审核

`AgentApprovalDialog.tsx`（147 行）现在的展示是
`JSON.stringify(current.args, null, 2)`（`:99-102`）。
④ 要写的是需求分析、项目背景、服务内容这类**几百字的中文散文**。
它在 JSON 里是一个把换行转义成 `\n` 的长字符串，挤在一个等宽字体块里，
**旁边还有倒计时在跑**。

用户面对这个只有一个现实选择：盲批。
那么"任何写操作都需要人工审核"这条要求就是**名义上成立、实质上落空**。
这跟本项目已经踩过四次的那族坑同源——**信号只对开发者可读**。

### 2. 文本比数字更需要"改后再批"

数字错了，用户能一眼看出并拒绝重说。散文不可能一次就对——
措辞、口径、详略总要调。若只能批准/拒绝，用户会陷入
"拒绝 → 重新描述 → 再看一遍 → 再拒绝"的循环，最后干脆自己手打。
**能改的审批才是能用的审批。**

因此本文分两阶段，**A 不过不做 B**。

## 阶段 A · 审批弹窗：能读、能对照、能改

### 已确认的关键事实

- 弹窗是 `src-ui/src/components/ai/AgentApprovalDialog.tsx`，147 行，
  展示 `toolName` + `JSON.stringify(args)`，带倒计时。
- `GATED_TOOLS`（`dsh-tool-lamber/src/approval.ts:38-40`）**目前只有一个条目**
  `write_test_marker`，说明这套机制至今只服务过一个无害的测试工具，
  **从未面对过真实业务写入**。
- 审批决定目前是布尔：`ai_resolve_approval(request_id, approved)`。
- 审批链路（`ApprovalGate`、`agent_approval_log`、超时/失败关闭）已通过四条路径真人验证，
  是目前最稳的一块。

### 要做的事

1. **按"写入意图"结构化展示，不是 JSON dump**：写哪个项目、哪张表、哪些字段，
   每个字段一行，长文本可完整阅读（可滚动/展开），不转义换行。
2. **必须显示新旧对照。** 字段原本有值时，要能看出这是**覆盖**还是**填空**——
   这是两个完全不同的决定，现在的展示分不出来。
3. **支持"修改后批准"**：用户可就地编辑将写入的值，再批准。
4. **审计必须同时记录模型原值与用户改后的值。**
   否则事后翻 `agent_approval_log` 无法判断某段文字是模型写的还是人改的——
   对签批材料来说这个可追溯性是必需的。
5. **倒计时要重新定。** 90 秒读一段 300 字需求分析、校对、再修改，不够。
   延长写类工具的时限并在 UI 说明；**但超时仍必须判拒绝**，不要为了体验改成默认通过。

### 边界：这是对审批机制唯一一次有意扩展

之前多份任务书写着"不碰审批机制"。**本阶段是例外，且只扩展这些**：
展示层、决定内容（从 bool 变为 bool + 可选的修改后参数）、审计字段。

**不得改动**：`ApprovalGate` 的超时与失败关闭语义、`gated_tool_names_match_the_plugin`
这类守卫、`GATED_TOOLS` 的判定位置、以及"未决即拒绝"的默认方向。

**Gate A：** 拿一段 300 字以上的真实需求分析文本走一次审批，
真人确认：能读完、能看出是覆盖还是填空、能改、改后写入的是改后的值、审计两版都在。
**做不到就不要进阶段 B。**

## 阶段 B · 写工具：填模板字段

### 已确认的关键事实

- ① 已经把"这张表有哪些字段、哪些为空"抽成了可复用的纯函数
  （需求表 11 项规则，同时供完成度、AI 上下文和聊天卡片使用）。
  **字段白名单从它派生，不要另写一套。**
- ① 同时把生成取值统一到了保存态。写入必须走**同一条保存链路**，
  不要新写 SQL，也不要绕过既有的保存/校验入口。
- ② 的项目绑定校验已就位：工具带可信 sessionId，Rust 侧核对绑定项目。

### 要做的事

0. **先补一个只读工具 `read_template_fields(templateId)`**（2026-09-07 补入，见下方"补充"）。
   **没有它，阶段 A 的新旧对照和阶段 B 的填写判断都无从谈起**——
   模型必须先知道现在填了什么、哪些是空的，才谈得上写。
1. **新增工具 `fill_template_fields(projectId, templateId, fields)`**，
   复用既有保存命令，不新写 SQL。
2. **登记进 `GATED_TOOLS`**，文案要说清将写入哪张表、哪些字段。
3. **硬边界：只允许写文本字段。**
   **金额、税率、年限、折现率、测算结果一律拒绝**——即使模型把它们塞进 `fields`。
   这些必须走测算引擎（路线图"架构决定"：直接写会绕过 `calculator.rs`，
   0 容差校验与税额闭合失效，且**不报错**）。
   拒绝要发生在**服务端**，不能只靠工具 schema 描述。
4. **走 ② 的绑定校验**：只能写当前会话绑定的项目；通用聊天会话**一律拒绝**
   （③ 只给聚合只读开了口子，不含写）。
5. **写入后要能回到模板页看见**，并让完成度清单同步更新——
   与 ① 建立的"两个入口写同一份数据"保持一致。

**Gate B：** 聊天里让 AI 写一段需求分析 → 审批弹窗读得懂 → 改一处 → 批准 →
回模板页看见改后的文本 → 完成度 +1 → 生成 docx 里是改后的文本。全链路真人走一遍。

6. **回归**：②的越权拒绝、③的聚合放行、审批原四条路径（确认/拒绝/超时/无工作区）全部通过。

# 补充（2026-09-07）：缺一个"读模板字段"的只读工具

> **本节修正原任务书的一个疏漏。** 原文只写了 `fill_template_fields`（写），
> 没写对应的读。**这是错的**——AI 要填字段，逻辑上必须先能读；
> 阶段 A 的"新旧对照"更是直接依赖读到旧值。

## 缘起：用户实测撞到

用户在绑定项目的会话里问"需求导入表填了什么"，模型答不上来，
并如实说明"本会话没有提供读取需求导入表模板字段内容的只读工具"。
同时 dsh 自带的 `bash` / `glob` 被拒，报
`LamberBridgeError: 该工具尚未定义项目权限，已拒绝调用`。

**模型的判断和行为都是对的**，它没有猜也没有编。要修的不是模型。

## 已确认的关键事实

### 1. `bash` / `glob` 被拒是 ② 的 fail closed 在正常工作，**不要给它们开权限**

三条理由，缺一不可：

1. **开了等于给限权体系开后门。** dsh 自带工具没有 `projectId` 概念，
   ②"绑定项目比对"对它们不适用。放行即意味着模型可绕过项目隔离读到任何项目的任何文件。
2. **它根本解决不了这个需求。** 模板表单值存在
   `project_template_states.filled_data_json`（`db.rs:246-256`），**不在文件里**；
   工作区 `templates/` 下的 `.docx` 是**空白模板**，读它拿不到任何填写值。
3. 所以开权限只会让模型多绕一圈再失败，同时永久性地削弱 ②。

### 2. 真实缺口：模板字段的可见性是**被动的**，且依赖当前页面

`src-ui/src/ai/context/buildAiChatContext.ts:58-65` 的 `buildRequestedSources`：
只有当 `activeTemplateId` 存在**且**当前视图是 `ict_lifecycle` / `ict` 时，
才请求 `["templates", "template_detail"]`；否则返回 `undefined`，
后端走默认摘要模式，**不含模板明细**。

而 `activeTemplateId` 来自 `activeModule?.startsWith("ict.template.")`——
即**用户此刻正打开着那张模板页**。

→ 用户在 AI 面板里问、而没开那个页面，模型就是看不到。这不是权限问题，是**没有主动查询的手段**。

### 3. 数据和规则都是现成的

- 值：`project_template_states.filled_data_json`
- "哪些字段、哪些为空"的规则：① 已抽成可复用纯函数（需求表 11 项），
  同时供完成度清单、AI 上下文和聊天卡片使用。**读工具复用它，不要另写一套。**

## 要做的事

1. **新增只读工具 `read_template_fields(templateId)`**：返回该模板在**当前绑定项目**下
   已保存的字段值 + 缺项清单（复用 ① 的纯函数）。
2. **不接受 `projectId` 参数**，项目一律取自 ② 的会话绑定——
   这样它天生就受项目隔离约束，不需要新的鉴权分支。
3. **不需要审批**（只读，先例：`run_benefit_calculation`、`query_projects`）。
4. **通用聊天会话拒绝**：它是项目内工具，不属于 ③ 那类聚合只读豁免。
5. **不返回本机路径**（`template_path` 等），与 ③ 的字段边界保持一致。
6. 长文本字段要能完整返回，但**要有总长上限**，超限时明示截断而非静默截断
   （沿用 ③ 的 limit 处理方式）。

## 不要做的事

- **不要给 `bash` / `glob` 或任何 dsh 自带工具开项目权限**（关键事实 1）。
  它们继续被拒是正确行为，不是待修缺陷。
- **不要改 `buildAiChatContext` 的页面相关注入逻辑**去"顺便让模型总能看到模板"。
  被动注入服务的是"用户正在看这一页"的场景，主动查询是另一件事，两者不要混。
  把注入范围放大只会让每轮对话都背上模板全文的上下文开销。
- 不要让读工具具备任何写能力，也不要用它做"读出来再原样写回"的迂回写入。
- 不改 `project_template_states` 结构与保存链路。

## 验证要求

1. 绑定项目 A 的会话读 A 的模板字段 → 放行且值正确（与模板页显示一致）。
2. **不开模板页**、仅在 AI 面板里提问 → 模型能通过工具拿到字段值。
   这是本补充要解决的原始场景，必须真实走一遍。
3. 绑定 A 的会话尝试读 B 的模板 → 拒绝（工具不收 `projectId`，应无从指定；
   若实现上仍可指定，必须服务端拒绝）。
4. 通用聊天会话调用该工具 → 拒绝。
5. `bash` / `glob` 仍被拒 → 确认本次改动**没有**顺手放开它们。
6. 返回值不含本机路径；超长内容按明示截断处理。
7. 回归：②的越权拒绝、③的聚合放行与字段边界全部继续通过。

# 补充二（2026-09-07）：图片上传卡片仍绑在"页面上下文"上

> **与上一节同根**：都是"能力被 `templateDetail` 是否在 AI 上下文里绑架"。
> 上一节解耦了**读字段**（`read_template_fields` 已实现），
> 但**图片上传卡片没跟着解耦**，两边现在不一致。

## 用户实测现场（2026-09-07）

用户在绑定项目的会话里贴了一张图，想加进需求导入表的附件。模型回答：

> 图片类字段我不可写……图片上传属于系统界面操作，无法通过聊天写入。

**"无法通过聊天写入"这半句是错的。** ① 那轮实现的正是"聊天里补图片入库"
（验证记录：*"聊天补两张图片→9/11、10/11、11/11→docx实际嵌图"*），
组件是 `src-ui/src/components/ai/DemandImageCompletionCard.tsx`。
只是**这次卡片没出现**，模型也不知道产品有这个能力，于是把用户引去了界面操作。

模型其余表现是对的：认出那张图其实是之前聊天回答的截图、没有把不相干的图当客户确认材料塞进去、
正确指出 `techItems`（动态清单）同样不可写。**要修的不是模型。**

## 已确认的关键事实

### 1. 卡片的触发条件绑在页面上

`src-ui/src/components/ai/AiChatPanel.tsx:400`：

```js
const hasDemandContext = composedContext.savedProjectContexts?.some(
  saved => saved.data.templateDetail?.templateId.includes('需求导入表')
);
```

而 `templateDetail` 只有在用户**正打开着需求导入表那一页**时才注入
（`buildAiChatContext.ts:58-65`，`activeTemplateId` + 视图为 `ict_lifecycle`/`ict`）。

→ **在 AI 面板里聊天时卡片不会出现**，因为上下文里没有 `templateDetail`。

### 2. 这个耦合本身就是设计错误

**上传卡片是产品 UI，不是模型上下文。** 它没有任何理由依赖
"注入给模型的那份上下文里有没有 templateDetail"。
前端完全可以用**绑定项目**直接读模板状态、算缺项、挂卡片——
这条路不经过模型，**不增加任何 prompt 开销**。

### 3. 需要的数据已经现成，且已有共享纯函数

`read_template_fields` 的 `completionItem`（`readTemplateFields.ts:8`）已含：

```ts
{ key, label, filled, evaluated, kind, templateName, usage }
```

**`usage` 正是 attach1 / attach2 的槽位标识**，`kind` 能区分 `image`，
`missingFields` 已经是 `evaluated && !filled` 的过滤结果。
算它的是共享纯函数 `getCatalogCompletion`（`readTemplateFields.ts:34`）。

→ 前端复用同一个函数即可，**不要再写第二套缺项判断**
（沿用 `build-contract.mjs` 那条原则）。

## 要做的事

1. **把卡片触发改为基于"绑定项目 + 缺项"**，不再基于
   `composedContext.savedProjectContexts` 里有没有 `templateDetail`。
   前端直接按绑定项目读模板状态、用 `getCatalogCompletion` 算缺项，
   取其中 `kind === 'image' && evaluated && !filled` 的条目生成 `DemandUploadTarget`。
2. **`usage` 从缺项条目直接取**，不要在前端另行拼 `attach1` / `attach2` 字符串。
3. **让模型知道这条能力存在**：工具/系统提示里说明"图片可由用户在聊天中的上传卡片补齐"，
   避免它继续告诉用户"只能去界面操作"。
   > 但仍要如实说明**模型自己不能写图片**——它只能提示用户用卡片，
   > 写入依旧由**用户点击**触发（① 确立的边界，不要改）。

## 不要做的事

- **不要为了让卡片出现而放宽 `buildAiChatContext` 的注入范围**
  （上一节已写死的理由：每轮对话都背上模板全文的上下文开销）。
  卡片走产品自己的数据通道，不走模型上下文。
- **不要给模型加"写图片"的工具**。① 确立的边界是写入由用户点击触发，
  这条不因本次改动而松动。
- 不要在前端另写一套缺项判断（关键事实 3）。
- 不改 `save_template_asset` 的存储路径、命名、20MB 与三格式限制。
- 不做动态清单（`techItems` 等 `list` 类）的写入——那与图片同属超范围项。

## 验证要求

1. **原始场景**：绑定项目、**不打开模板页**，在 AI 面板里问"附件1 还没传吧"，
   确认上传卡片出现，点它上传后图片进入 attach1 槽位、完成度 +1。
   这是本节要解决的场景，必须真实走一遍。
2. **已打开模板页时行为不变**（回归 ① 的既有路径）。
3. **模型口径**：确认它不再说"无法通过聊天写入"，而是引导用户使用卡片；
   同时仍如实说明自己不能直接写图片。
4. 生成 docx，确认从卡片补的图真的嵌进附件位置（沿用 ① 的验收方式）。
5. 未绑定项目 / 通用聊天会话：确认不出现卡片。
